# Pinned-provider compatibility

Reviewed the installed `better-auth@1.4.9` and `@convex-dev/better-auth` implementations rather than relying on newer provider examples.

- `oidc-provider/authorize.mjs` checks exact registered redirect URIs and stores the nonce, S256 challenge, client and subject in an expiring verification record.
- `oidc-provider/index.mjs` validates client/redirect/PKCE during code exchange and consumes the code. With `useJWTPlugin`, its ID token has the client ID as audience and `user.id` as subject. This is distinct from MCP access tokens.
- Better Auth 1.4.9's MCP plugin exposes its own `/mcp/authorize` and `/mcp/token`, plus shared OIDC consent. It does not expose the OIDC authorize/token/UserInfo routes or use OIDC trusted clients for its MCP token exchange. `convex/lib/homepageOidc.ts` explicitly registers those three maintained OIDC endpoints for the configured confidential homepage client, without installing a second automatic login hook. Homepage uses `/api/auth/oauth2/authorize`, `/api/auth/oauth2/token` and `/api/auth/oauth2/userinfo`.
- An unauthenticated homepage authorization redirects to Tasky's frontend with the original query, without setting `oidc_login_prompt` (which the existing MCP login hook owns). The Next.js login bridge resumes the OIDC endpoint using the frontend's stored Better Auth session. The existing shared consent endpoint handles the provider's consent code. Other MCP clients retain their existing route.
- General OpenID discovery is overridden by the Convex plugin. JWKS is forwarded to `/api/auth/convex/jwks`; the JWT plugins use the same component key table. Identity signatures are explicitly checked against the configured issuer's keys on callback, never on an ordinary page load.
- The refresh branch returns an opaque access token and a new refresh token, **without** an ID token. The client processes that response and calls OIDC UserInfo to bind it back to the original subject. The provider checks refresh-token expiry and client ID, but its pinned refresh implementation does not check the client secret. The homepage adapter requires the configured `client_secret_post` credentials before either grant type, comparing SHA-256 digests without early exit. Its default seven-day refresh lifetime is unchanged.
- MCP shares the OIDC verification and access/refresh-token stores. `convex/lib/homepageMcp.ts` wraps the original MCP endpoints: token exchange checks the credential's stored client ID and rejects homepage refresh grants and authorization codes before the MCP implementation can issue tokens or consume codes. Caller-supplied client IDs, Basic authentication and JSON coercion cannot bypass this boundary. The guard remains installed when homepage OIDC is disabled. Keep the configured homepage client ID reserved; revoke old grants before changing that ID.
- The MCP session endpoint returns the entire grant, including its refresh credential. Homepage access tokens therefore return no MCP session, both over HTTP and through the server API used by `withMcpAuth`. OIDC UserInfo remains available for the homepage's legitimate renewal flow. Ordinary MCP clients continue using the original registration, authorization and token implementations.
- The pinned provider creates a new refresh record without deleting the previous one. Homepage retains only the latest encrypted token and locally revokes its remembered grant on logout. It does not claim global token-family revocation or change other MCP grant lifetimes.
- `convex/homepageOidc.test.ts` exercises the actual installed Better Auth package with an isolated in-memory adapter: frontend login redirect, consent, S256 exchange, JWKS signature/subject/audience/nonce, consumed code rejection, confidential renewal and UserInfo subject. Cross-endpoint tests cover form/JSON/Basic credentials, changed or missing client IDs, coercible JSON, code preservation, grant-store integrity, MCP session isolation, and disabling OIDC. Public and confidential MCP clients complete real registration, consent, code exchange, renewal and resource authentication. Worker tests separately cover client protocol behavior and state/grant storage. Production account sign-in remains a required rollout check.
- After any auth-package upgrade, rerun these integration and protocol tests and a live sign-in, renewal, and logout. Do not switch issuer/audience or route paths using unrelated access-token metadata.

Protocol implementation: [oauth4webapi](https://github.com/panva/oauth4webapi). Signature verification: [jose](https://github.com/panva/jose). Single-use login state and grant renewal run in serialized Durable Objects, outside KV and the normal read path.
